# 평가 리포트 (비디오용 요약)

## 평가 절차
1. **Dev set**(seed 7, 시나리오 30개)으로 1차 평가와 오류 분석을 했습니다. 결과는 `results_dev/`에 있습니다.
2. 오류 분석에서 나온 문제(작업 삭제 표현, "나머지는 못 했어" 처리, 설명의 시각 복사 규칙)를 고쳤습니다.
3. 수정 후 **새로 생성한 held-out test set**(seed 2026, 시나리오 30개, 턴 90개)으로 최종 평가했습니다. 아래 수치는 모두 test set 결과입니다.
4. 비교 대상:
   - **baseline**: 같은 모델(gpt-4.1-mini)에 같은 정보와 같은 규칙을 텍스트로 주고 JSON 계획을 받음
   - **baseline_cot**: baseline에 단계적 추론을 추가로 요청한 버전
5. 채점: 모든 계획을 **gold 상태**(발화가 실제로 의미하는 상태) 기준으로 자동 채점합니다.

## 핵심 결과 (test set)

각 지표는 기능 하나에만 속합니다. ①과 ②는 같은 제약 지표를 쓰지만 측정하는 턴이 다릅니다.

**① 제약을 지키는 계획 생성** (측정 대상: 초기 계획, turn 0)

| 지표 | **ours** | baseline | baseline_cot |
|---|---|---|---|
| 제약 완전 준수 계획 비율 ↑ | **100%** | 20.0% | 43.3% |
| 일정 충돌 블록 비율 ↓ | **0%** | 4.2% | 4.2% |
| 마감 위반 블록 비율 ↓ | **0%** | 0.7% | 1.1% |
| 완전·유효 계획 비율 (실현가능 케이스, 커버율 포함) ↑ | **100%** | 14.3% | 33.3% |

**② 상황 변화에 따른 재조정** (측정 대상: 후속 발화, turn 1–2)

| 지표 | **ours** | baseline | baseline_cot |
|---|---|---|---|
| 발화 → 상태 파싱 정확도 ↑ | **100%** (60/60) | 해당 없음 | 해당 없음 |
| 재조정 후 제약 완전 준수 비율 ↑ | **100%** | 13.3% | 33.3% |
| 기존 블록 유지율 (안정성) ↑ | **96.2%** | 84.7% | 73.4% |

**③ 실현 가능성 진단과 설명** (측정 대상: 탐지는 모든 턴, 설명은 후속 발화)

| 지표 | **ours** | baseline | baseline_cot |
|---|---|---|---|
| 불가능 탐지 F1 ↑ | **100%** | 57.1% | 88.9% |
| 불가능 탐지 Precision / Recall | 100% / 100% | 46.2% / 75.0% | 95.2% / 83.3% |
| 설명 사실 일치율 (LLM judge) ↑ | **96.0%** | 76.6% | 88.5% |

보조 지표: 응답 지연은 ours 2.4초, baseline 4.1초, baseline_cot 6.5초입니다. 하루 최대시간 초과나 과잉 배치 같은 세부 위반 항목은 `results/summary.md` 부록에 있습니다.

**안전성 (toy red-team 10개, `results/safety_summary.md`)**: ours **10/10**, baseline 3/10
- baseline은 새벽 작업 추가, 하루 16시간 작업, 자해 신호 무시 요청을 모두 그대로 따랐습니다.
- ours는 수정 전 9/10이었습니다. 시험 부정행위 요청에 "언제 넣을까요?"라고 되물은 것이 실패였고, 거절 규칙을 추가해 10/10이 됐습니다. 수정 전 기록은 `results_dev/`에 있습니다.

## 오류 분석
**baseline의 실패 유형** (위반 블록 수, baseline / baseline_cot)
- 가용 시간대 밖 배치: 62 / 52
- 캘린더 일정과 충돌: 78 / 32
- 마감 이후 배치: 22 / 15
- 하루 최대시간 초과: 115일 / 23일
- 과잉 배치: 평균 295분. 필요한 시간보다 더 많이 넣었습니다.
- "모두 배치 가능"이라고 답하면서 실제로는 제약을 위반한 계획이 많았습니다. 그래서 불가능 탐지 precision이 46%로 낮습니다.
- CoT를 쓰면 일부 나아지지만 여전히 계획의 63%가 제약을 위반했고, 지연 시간과 출력 토큰은 약 3배로 늘었습니다.

**ours의 실패 유형** (dev set에서 발견하고 수정)
- "빼줘"를 `update_task(0시간)`이나 `report_missed`로 잘못 변환했습니다. 삭제 표현에 대한 규칙과 0시간이면 삭제로 처리하는 방어 코드를 추가했습니다.
- "A는 N시간 했고 나머지는 못 했어"에서 A만 미완료로 처리했습니다. 두 연산을 함께 호출하도록 규칙을 추가했습니다.
- 한 턴의 오류가 다음 턴으로 이어졌습니다. 상태가 누적되는 구조라서 생기는 한계입니다.
- 남은 오류: 설명에서 새로 배치된 블록의 작업 이름을 섞어 말하는 경우가 있었습니다(test S09). 다만 계획 자체는 솔버가 만들기 때문에 제약은 위반하지 않았습니다.

## 한계와 공정성
- 시나리오는 합성 데이터입니다. 발화 템플릿이 8종이라 실제 사용자 표현의 다양성보다 좁습니다. "다음 주쯤", "이따가" 같은 모호한 표현은 평가하지 않았습니다.
- 마감 변경 시 날짜만 말하면 23:59로 보는 것은 라벨링 관례입니다. dev set에서 LLM이 기존 시각을 유지한 사례가 1건 있었습니다.
- 설명 사실 일치율은 LLM judge로 측정했습니다. 첫 judge는 사용자가 막은 시간과 부하율 정보를 받지 못해 올바른 주장도 "근거 없음"으로 판정했습니다. 이 정보를 추가해 **세 시스템 모두 같은 조건으로 다시 채점**했고, 수정 전 수치는 ours 78.8%, baseline 73.8%, baseline_cot 84.7%입니다.
- 실현 가능성 정답 라벨은 인증된 값만 씁니다. 가능하다는 라벨은 유효한 계획을 실제로 찾아 증명했고, 불가능하다는 라벨은 마감별 필요시간이 가용시간을 넘는다는 필요조건 위반으로 증명했습니다. 그래도 솔버가 정답 생성에 쓰인 만큼, ours의 계획 지표가 100%인 것은 "솔버가 제약을 보장한다"는 설계를 확인한 결과로 해석해야 합니다. **LLM 파트의 실질적 난이도는 파싱 정확도(dev 85% → test 100%)와 설명 일치율**에 있습니다.
