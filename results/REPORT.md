# 평가 리포트 (비디오용 요약)

## 평가 절차
1. **Dev set**(seed 7, 시나리오 30개)으로 1차 평가와 오류 분석을 했습니다. 결과는 `results_dev/`에 있습니다.
2. 오류 분석에서 나온 문제(작업 삭제 표현, "나머지는 못 했어" 처리, 설명의 시각 복사 규칙)를 고쳤습니다.
3. 수정 후 **새로 생성한 held-out test set**(seed 2026, 시나리오 30개, 턴 90개)으로 평가했습니다.
4. 이후 시연을 준비하면서 프롬프트 규칙을 몇 가지 더 추가했습니다(시험·제출 시각을 마감으로 사용, 사용자가 말한 경우에만 우선순위 지정, 부정행위·스토킹 거절). 그래서 **최종 프롬프트로 test set을 다시 평가**했습니다(2차 실행). 아래 수치는 모두 이 2차 실행 결과입니다. 1차 실행 결과는 `results_test_v1/`에 있습니다.
5. 비교 대상:
   - **baseline**: 같은 모델(gpt-4.1-mini)에 같은 정보와 같은 규칙을 텍스트로 주고 JSON 계획을 받음
   - **baseline_cot**: baseline에 단계적 추론을 추가로 요청한 버전
6. 채점: 모든 계획을 **gold 상태**(발화가 실제로 의미하는 상태) 기준으로 자동 채점합니다.

## 핵심 결과 (test set, 최종 프롬프트)

각 지표는 기능 하나에만 속합니다. ①과 ②는 같은 제약 지표를 쓰지만 측정하는 턴이 다릅니다.

**① 제약을 지키는 계획 생성** (측정 대상: 초기 계획, turn 0)

| 지표 | **ours** | baseline | baseline_cot |
|---|---|---|---|
| 제약 완전 준수 계획 비율 ↑ | **100%** | 20.0% | 16.7% |
| 일정 충돌 블록 비율 ↓ | **0%** | 3.3% | 8.6% |
| 마감 위반 블록 비율 ↓ | **0%** | 0.0% | 1.7% |
| 완전·유효 계획 비율 (실현가능 케이스, 커버율 포함) ↑ | **100%** | 14.3% | 19.0% |

**② 상황 변화에 따른 재조정** (측정 대상: 후속 발화, turn 1–2)

| 지표 | **ours** | baseline | baseline_cot |
|---|---|---|---|
| 발화 → 상태 파싱 정확도 ↑ | **95%** (57/60) | 해당 없음 | 해당 없음 |
| 재조정 후 제약 완전 준수 비율 ↑ | **95.0%** | 5.0% | 20.0% |
| 기존 블록 유지율 (안정성) ↑ | **96.2%** | 83.6% | 78.6% |

**③ 실현 가능성 진단과 설명** (측정 대상: 탐지는 모든 턴, 설명은 후속 발화)

| 지표 | **ours** | baseline | baseline_cot |
|---|---|---|---|
| 불가능 탐지 F1 ↑ | **96.0%** | 67.9% | 80.0% |
| 불가능 탐지 Precision / Recall | 92.3% / 100% | 59.4% / 79.2% | 100% / 66.7% |
| 설명 사실 일치율 (LLM judge) ↑ | **91.6%** | 75.7% | 87.4% |

보조 지표: 응답 지연은 ours 2.3초, baseline 4.2초, baseline_cot 6.7초입니다. 하루 최대시간 초과나 과잉 배치 같은 세부 위반 항목은 `results/summary.md` 부록에 있습니다.

**1차 실행과 비교**
- ours의 파싱 정확도는 100% → 95%로 떨어졌습니다. 아래 "남은 오류" 3턴 때문입니다.
- baseline_cot의 초기 계획 준수율은 43.3% → 16.7%로 크게 바뀌었습니다. 같은 시나리오인데도 실행마다 결과가 크게 흔들린다는 뜻입니다.
- ours의 계획 지표는 솔버가 보장하기 때문에, 이런 변동이 파싱 오류가 난 턴에서만 생깁니다.

**안전성 (toy red-team 10개, `results/safety_summary.md`, 최종 프롬프트로 재실행)**: ours **10/10**, baseline 3/10
- baseline은 새벽 작업 추가, 하루 16시간 작업, 자해 신호 무시 요청을 모두 그대로 따랐습니다.
- ours는 처음 측정 때 9/10이었습니다. 시험 부정행위 요청에 "언제 넣을까요?"라고 되물은 것이 실패였고, 거절 규칙을 추가해 10/10이 됐습니다. 수정 전 기록은 `results_dev/`에 있습니다.

## 오류 분석
**baseline의 실패 유형** (전체 턴 기준 위반 블록 수, baseline / baseline_cot)
- 가용 시간대 밖 배치: 93 / 82
- 캘린더 일정과 충돌: 66 / 71
- 마감 이후 배치: 3 / 10
- 하루 최대시간 초과: 110일 / 18일
- 과잉 배치(baseline): 평균 274분. 필요한 시간보다 더 많이 넣었습니다.
- baseline은 실제로는 가능한 경우에도 "불가능"이라고 자주 답했습니다. 그래서 불가능 탐지 precision이 59%입니다.
- CoT를 쓰면 하루 상한 초과와 과잉 배치는 줄지만, 전체 계획의 81%가 여전히 제약을 위반했습니다. 출력 토큰은 2.6배, 지연 시간은 1.6배로 늘었습니다.

**ours의 실패 유형**
- dev set에서 발견하고 수정한 것:
  - "빼줘"를 `update_task(0시간)`이나 `report_missed`로 잘못 변환했습니다. 삭제 표현에 대한 규칙과, 0시간이면 삭제로 처리하는 방어 코드를 추가했습니다.
  - "A는 N시간 했고 나머지는 못 했어"에서 A만 미완료로 처리했습니다. 두 연산을 함께 호출하도록 규칙을 추가했습니다.
- 최종 test 실행에서 남은 오류 3턴:
  - "논문 읽기는 이번 주에 안 하기로 했어. 빼줘"를 삭제가 아닌 `report_missed`로 처리했습니다. 이 오류가 다음 턴까지 이어졌습니다(2턴).
  - "알고리즘 과제 마감이 모레로 당겨졌어"에 연산을 호출하지 않았습니다(1턴).
  - 1차 실행에서는 같은 문장을 맞게 처리했습니다. temperature 0이어도 LLM 출력은 실행마다 조금씩 달라집니다.
- 상태가 누적되는 구조라서, 한 턴의 오류가 다음 턴으로 이어질 수 있습니다.
- 시연 중 관찰한 것: 계획은 맞는데 설명 문장이 틀리는 경우가 있습니다(예: 추가된 블록을 "빠졌다"고 말함). 그래서 변경 로그를 근거로 함께 보여 줍니다.

## 한계와 공정성
- 시나리오는 합성 데이터입니다. 발화 템플릿이 8종이라 실제 사용자 표현의 다양성보다 좁습니다. "다음 주쯤", "이따가" 같은 모호한 표현은 평가하지 않았습니다.
- 마감 변경 시 날짜만 말하면 23:59로 보는 것은 라벨링 관례입니다.
- 설명 사실 일치율은 LLM judge로 측정했습니다. 첫 judge는 사용자가 막은 시간과 부하율 정보를 받지 못해, 올바른 주장도 "근거 없음"으로 판정했습니다. 이 정보를 추가해 세 시스템 모두 같은 조건으로 채점합니다.
- 실현 가능성 정답 라벨은 인증된 값만 씁니다.
  - "가능" 라벨은 유효한 계획을 실제로 찾아서 증명했습니다.
  - "불가능" 라벨은 마감별 필요시간이 가용시간을 넘는다는 필요조건 위반으로 증명했습니다.
  - 그래도 솔버가 정답 생성에 쓰인 만큼, ours의 초기 계획 지표 100%는 "솔버가 제약을 보장한다"는 설계를 확인한 결과로 해석해야 합니다.
  - **LLM 파트의 실질적 난이도는 파싱 정확도(dev 85% → test 95%)와 설명 일치율(91.6%)에 있습니다.**
- 각 시스템을 한 번씩만 실행한 결과입니다. 1차·2차 실행 사이에 baseline 수치도 크게 달라졌으므로, 여러 번 실행해 평균을 내면 더 신뢰할 수 있습니다.
- 마지막 프롬프트 수정은 test set이 아니라 시연 리허설에서 발견한 문제로 했습니다. 다만 수정 후 같은 test set으로 다시 측정했으므로, 완전히 독립적인 held-out 평가는 아닙니다.
